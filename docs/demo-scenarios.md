# Лабораторная работа № 4. Проверка сценариев

Оба сценария запускаются на локальном стенде с ключом `--demo-faults`. Клиент выполняет запросы только через Gateway. Каждый прогон создаёт два товара с уникальными идентификаторами и синтетический CSV из 14 недель с продажами по 20 единиц в неделю.

Запустите сервер из корня репозитория в первом окне PowerShell.

~~~powershell
.\.venv\Scripts\python.exe -m services.runner --demo-faults
~~~

Во втором окне запустите проверку.

~~~powershell
.\.venv\Scripts\python.exe -m postman.demo --scenario all
~~~

Для запуска по отдельности используются значения `--scenario happy` и `--scenario failure`. При другом порте передайте `--url http://127.0.0.1:8081`. Скрипт проверяет HTTP-ответы, ожидает фоновые переходы и завершится с ошибкой, если любое ожидаемое условие не выполнено.

## 1. Импорт, закупка и приёмка

| Действие | Взаимодействие | Что проверяется |
| --- | --- | --- |
| Создать остаток 10 и загрузить CSV | Gateway → inventory и sales, публичный HTTP | Корректировка возвращает 201, импорт — 202. В завершённом импорте 14 принятых строк и новая версия данных. |
| Получить рекомендацию | Sales публикует `sales.imported`. Forecast получает историю по REST и публикует `forecast.completed`. Replenishment читает прогноз и склад по REST. | Рекомендация появляется автоматически. Целевой уровень 40, позиция запаса 10, к закупке 30. |
| Оформить закупку и повторить запрос с тем же ключом | Gateway → procurement. Procurement вызывает claim в replenishment и создаёт план в inventory по REST. | Оба запроса возвращают один и тот же заказ и исходный статус `PREPARING`. В заказе подтверждаются 30 единиц. |
| Дождаться обновления склада и рекомендации | `purchase-order.confirmed` раздаётся брокером двум подписчикам. | Заказ и план переходят в `CONFIRMED`, рекомендация в `APPLIED`. Пока фактический остаток равен 10. |
| Зарегистрировать приёмку и повторить запрос | Gateway → inventory. Inventory публикует `stock.received`, procurement обрабатывает событие. | Повтор возвращает исходную приёмку. Остаток увеличивается с 10 до 40 ровно один раз. Заказ переходит в `RECEIVED`. |

Ожидаемый вывод содержит последовательность `PREPARING → CONFIRMED → RECEIVED`, рекомендацию `APPLIED` и изменение остатка `10 → 40`.

## 2. Конфликт запаса и компенсация

| Действие | Взаимодействие | Что проверяется |
| --- | --- | --- |
| Создать остаток 10, импортировать историю, получить рекомендацию 30 | Тот же рабочий путь через Gateway, HTTP и события | У рекомендации свежая версия запаса, статус `READY`. |
| Приостановить выполнение шага `PLAN` и оформить заказ | Admin вызывает `POST /__demo/planning/pause`. Procurement делает HTTP-вызов `claim`. | Сага дошла до `PLAN`. Рекомендация `CLAIMED`, закреплена за этим `orderId`. |
| Увеличить остаток на 7 и возобновить шаг `PLAN` | Обычный `POST /api/v1/inventory-adjustments`, затем `POST /__demo/planning/resume`. | Остаток 17. Версия склада стала 2, в закреплённой рекомендации осталась 1. |
| Попытаться создать план | Procurement → inventory, внутренний `POST /internal/v1/inbound-plans`. | Склад сам возвращает `409 STOCK_VERSION_CONFLICT`. |
| Завершить компенсации | Procurement вызывает `cancel` в inventory и `release` в replenishment. Затем публикует `purchase-order.cancelled`. | Заказ `CANCELLING → CANCELLED`. Склад сохраняет запись отмены по `orderId`, чтобы запоздавший запрос не создал поставку. Рекомендация `STALE`, закрепление снято. |
| Пересчитать количество | `POST /api/v1/recommendations` с тем же `forecastId`. | Новый снимок склада даёт новую рекомендацию на 23 единицы. Остаток 17, подтверждённых поступлений по отменённому заказу нет. |

Ожидаемый вывод содержит `STOCK_VERSION_CONFLICT → CANCELLED` и рекомендацию `STALE`. После пересчёта к закупке 23 единицы.

## Реальные взаимодействия и заглушки

- Публичные запросы, пять синхронных связей между бизнес-сервисами и обе компенсации проходят по HTTP между отдельными слушателями FastAPI. У каждого бизнес-сервиса свой файл SQLite.
- Локальный адаптер [брокера](../mocks/broker.py) заменяет RabbitMQ. Он проверяет схемы событий, маршрутизирует их по очередям подписчиков, хранит сообщения в своём SQLite и поддерживает повторы и DLQ. Обработчики событий и их изменения данных выполняют сами сервисы.
- [Локальная авторизация](../mocks/auth.py) заменяет Keycloak. Gateway выдаёт подписанные учебные JWT для выбранной роли. Сервисы проверяют токен, роль и канал доступа.
- Пауза нужна для воспроизводимого порядка действий. Она приостанавливает отправку запроса на шаге `PLAN`. Ошибка `409` возникает в складском сервисе после обычной корректировки запаса.
- Для аудита найдите в журнале сервера `correlationId` из строки демонстрации. По нему видны REST-запросы, события и шаги саги.

## Автоматическая проверка

~~~powershell
.\.venv\Scripts\python.exe -m unittest discover -s tests -v
~~~

Модульные тесты проверяют CSV, расчёт трёх прогнозов, формулу пополнения, защиту от запоздалого создания плана и DLQ. Интеграционные тесты поднимают HTTP-слушатели с временными базами SQLite и проверяют оба сценария, права и закрытые маршруты, идемпотентность при параллельном повторе, статус фонового прогноза, отмену и восстановление саги после перезапуска.
